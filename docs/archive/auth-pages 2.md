## Clerk gotchas (read this before touching Clerk-styled UI again)

Three real bugs were found and fixed here, each requiring a different verification technique because the previous one wasn't enough:

1. **Full-bleed layout, no containment.** Original layout stretched two panels to fill the entire viewport with content pinned near the top. Fixed by wrapping in a `pageBg` (viewport-height, flex-centered) around a `container` sized to its own content. Verified with plain screenshots at multiple viewport sizes — sufficient for a pure-layout bug.

2. **Asymmetric border-radius on pill buttons.** The Continue/Apple/Google buttons had a full pill radius on their left corners but a visibly smaller, squared-off radius on the right. Not visible in an unzoomed screenshot — only found by cropping and upscaling with `sips` (no ImageMagick available locally: `sips -c <h> <w> --cropOffset <y> <x> file.png` then `sips -z <h> <w> file.png` to upscale). Root cause was never fully confirmed (Clerk's actual component styles load dynamically from their CDN, not inspectable in `node_modules`) — worked around by setting `borderRadius` explicitly on `formButtonPrimary`/`socialButtonsBlockButton`/`formFieldInput` in `clerkAppearance.ts` instead of relying on the shared `variables.borderRadius`.

3. **The real corner-clipping bug, found after #2 didn't fully fix it.** User reported the same "cropped corners" complaint after fix #2 shipped. A fresh screenshot at that point, zoomed in the same way as #2, looked completely clean — no visible defect. This was the key lesson: **a screenshot that looks clean is not proof the bug is gone.** Connected directly to the user's own already-running dev server (note: `pkill -f "next dev"` earlier in the session did _not_ actually stop it — an independently-started `next dev` process survived) and used `getComputedStyle()` on the live `.cl-*` DOM tree instead of another screenshot. Found `.cl-cardBox` — a Clerk-internal wrapper distinct from `.cl-card` (which fix #2 had already touched) — ships with its own `border-radius: 24px` and `overflow: hidden`, and the Continue button's rendered width was measured as _exactly_ equal to cardBox's width (360px = 360px, zero gap). So cardBox's own rounded corners were clipping across the button/input corners even though the button's own radius computed as a perfect, uniform 999px pill. Fixed with `cardBox: { borderRadius: '0', overflow: 'visible' }` — `AuthLayout`'s own container already provides the single outer rounded card, so Clerk's nested rounding there was redundant as well as the actual bug.

**Takeaway for next time:** when a Clerk visual bug doesn't fully resolve after a plausible fix, check `getComputedStyle()` — specifically `overflow` and `border-radius` — on _every_ ancestor in the `.cl-*` DOM tree before trusting another screenshot, however closely zoomed. The visual severity of a clipping bug depends on how the clipping parent's radius compares to the child's, so it can range from obviously broken to nearly invisible depending on exact values.

## Other conventions established here (kept active, not archived)

- **CSS Grid:** use `minmax(0, 1fr)` rather than plain `1fr` for `grid-template-columns` — a plain `1fr` track won't shrink below its content's min-content width, which caused a silent mobile overflow (clipped invisibly by a parent's `overflow: hidden` rather than showing a scrollbar). This is now the default on this project; see `/docs/design-system.md`.
- **Clerk branding removal:** hiding "Secured by Clerk" via `elements.footer` is a supported technical option, but whether it's _allowed_ under Clerk's ToS for this account's plan tier was never confirmed — flagged to the user as an open item, not resolved here.
- **Next.js dev-mode indicator:** the stray "N" badge the user initially flagged as a brand issue was Next.js's own dev-mode route indicator, unrelated to Clerk or this page — disabled globally via `devIndicators: false` in `next.config.ts`, confirmed it never renders in production.
