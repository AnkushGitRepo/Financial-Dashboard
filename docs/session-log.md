## 2026-09-04 — Auth page composition fix: contained/centered card, two real bugs found

- Did: User flagged the auth pages as broken — two full-bleed panels stretching the whole viewport, content top-anchored, huge empty gap below, and sign-in/sign-up starting at different vertical positions since nothing centered against a shared reference point. Rebuilt `AuthLayout` around a single contained, vertically-centered card (`pageBg` = full-viewport flex-centered decorative gradient wrapper; `container` = the actual two-column card, sized to content, not stretched) so both pages now center the same way regardless of form height. Added a fade+slight-upward entrance on the container (Framer Motion, `useReducedMotion()`-gated), matching the landing page's motion language. Disabled the Next.js dev-mode route indicator (`devIndicators: false` in `next.config.ts`) — the stray "N" badge the user flagged is that indicator, not a brand element; confirmed it never appears in production, only local dev.
- Found two real bugs while verifying at the user's actual viewport size (a large monitor, ~2940×1614): (1) `grid-template-columns: 1fr 1fr` on `.container` doesn't let a track shrink below its content's min-content width — harmless at the sizes tested so far, fixed defensively with `minmax(0, 1fr)`. (2) The actual mobile-overflow bug: Clerk's `.cl-rootBox` renders at its own intrinsic width (~350px) regardless of its parent's actual width, so on a 390px viewport it blew out past the card and got silently clipped by the card's `overflow: hidden` (needed for the rounded corners) rather than showing a scrollbar — invisible unless you check computed layout, not just look for an obvious visual overflow. Fixed by adding `rootBox: { width: '100%' }` and `cardBox: { width: '100%' }` to `clerkAppearance.ts` — Clerk's `card` element alone wasn't enough since `rootBox` sits above it in Clerk's DOM and was never told to shrink. Verified at 390px, 820px (tablet breakpoint), 1440px, and ~1470×960 (matching the user's reported size) — clean at all four.
- Decided: Nothing new architecturally — this was a composition/bug-fix pass on the existing design, not a new pattern. `minmax(0, 1fr)` on grid tracks is now the default we reach for on this project rather than plain `1fr`, given it silently broke once already.
- Next: Same as above.

## 2026-09-04 — Asymmetric border-radius on Clerk pill buttons

- Did: User reported the Continue/Apple/Google buttons and input fields looked crowded against the container edges. First reproduction attempt (no screenshot attached) found the opposite — the form panel had _more_ padding than the carousel panel — so asked for the screenshot to be resent rather than guessing. Once received and zoomed in (via `sips` crop/upscale, no ImageMagick available locally), the real bug was visible: the Continue and Apple buttons had a full pill radius on their left corners but a visibly smaller, squared-off radius on their right corners — Clerk's shared `variables.borderRadius` was applying unevenly per-corner on pill-shaped buttons for reasons not visible from our side (Clerk's actual component styles load dynamically from their CDN, not inspectable in `node_modules`). Fixed by setting `borderRadius: 'var(--radius-pill)'` explicitly on `formButtonPrimary` and `socialButtonsBlockButton`, and `var(--radius-sm)` on `formFieldInput`, in `clerkAppearance.ts` — bypassing reliance on Clerk's variable propagation entirely for these elements. Verified fixed on both `/sign-in` and `/sign-up` via cropped/zoomed screenshots.
- Decided: Don't rely on Clerk's `variables.borderRadius` alone for elements where the exact corner rendering matters — set `elements.<name>.borderRadius` explicitly per element instead. Worth remembering if another Clerk-styled element shows a similar visual inconsistency later.
- Next: Same as above.

## 2026-09-04 — Real cause of "cropped corners" found: Clerk's own cardBox was clipping

- Did: User reported the same issue persisting after the previous fix — pixel-zoomed inspection of their newly-attached screenshot this time showed clean, correctly-rounded corners with no visible clipping, which didn't match "still seeing the same issue." Rather than guess again, connected directly to the user's own already-running dev server (`npm run dev` had been started independently — killing `next dev` processes during cleanup earlier this session did not actually stop it, worth remembering) and read `getComputedStyle()` on the actual DOM elements instead of relying on any more screenshots. Found the real bug: `.cl-cardBox` (a Clerk-internal wrapper distinct from `.cl-card`, which we had already styled) ships with its own `border-radius: 24px` and `overflow: hidden` — and the Continue button's rendered width was measured as exactly equal to cardBox's width (360px = 360px, zero gap), so cardBox's own rounded corners were clipping straight across the button's corners despite the button's own border-radius being a computed-correct, perfectly uniform 999px pill (confirmed directly via `getComputedStyle` — the previous session's radius-asymmetry fix was real and necessary, but not sufficient, since this second, independent clipping source was never touched). Fixed by setting `cardBox: { borderRadius: '0', overflow: 'visible' }` in `clerkAppearance.ts` — our own `AuthLayout` container already provides the single outer rounded card, so Clerk's own nested rounding on `cardBox` was redundant as well as actively harmful. Verified via computed styles (`border-radius: 0px`, `overflow: visible`) and a fresh screenshot.
- Decided: When a Clerk visual bug doesn't fully resolve after a plausible-looking fix, check `getComputedStyle()` on every ancestor in the `.cl-*` DOM tree for `overflow` + `border-radius` combinations before assuming the fix didn't work or trying another screenshot-based guess — screenshots (and even careful pixel-zooming) can look clean while a real, measurable clipping bug is still present, because the visual effect can be subtle depending on how the clipping parent's radius compares to the child's.
- Next: Same as above.
